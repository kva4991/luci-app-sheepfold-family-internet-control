# ADR-0014: один backend-вызов и отдельные UI-подписчики

- Статус: Принято
- Дата: 2026-07-27
- Теги: `§actsub1`
- Связанные документы: `docs/frontend-architecture.ru.md`, `docs/luci-command-actions.ru.md`

## Контекст

Одна изменяющая команда может почти одновременно запускаться из нескольких мест
LuCI. Повторять мутацию опасно, поэтому `core/backend/actions.js` объединяет
одинаковый стабильный ключ в одну выполняющуюся операцию.

Прежняя реализация возвращала всем инициаторам один и тот же Promise. В результате
выполнялись callbacks только первого вызова: другая панель могла не перечитать
данные, не закрыть своё окно или не показать собственную ошибку, хотя состояние
роутера уже изменилось.

## Рассмотренные варианты

1. Выполнять backend-команду для каждого инициатора. Отклонено: неидемпотентная
   мутация может примениться дважды.
2. Возвращать общий Promise и callbacks первого инициатора. Отклонено: интерфейс
   разных панелей расходится с фактическим состоянием.
3. Выполнить одну backend-операцию и создать отдельную callback-цепочку каждому
   UI-инициатору. Выбрано.

## Решение

- `action-key` определяет одну backend-операцию;
- каждый вызов получает отдельный Promise-подписку;
- каждый подписчик выполняет свои `onSuccess`, `refresh`, `onError` и уведомление;
- все связанные элементы управления остаются занятыми, пока завершены не только
  backend, но и callbacks всех подписчиков;
- ошибка callback одного экрана не запускает backend повторно и не отменяет
  обновление другого экрана.

## Последствия

Backend защищён от повторной мутации, а каждая панель получает честное локальное
состояние. Возвращаемые Promise двух вызовов с одинаковым ключом намеренно разные,
хотя лежащая под ними операция одна. Это закреплено тестом
`tests/luciCommandActions.test.mjs`.

## Проверка

- `node --test tests/luciCommandActions.test.mjs`
- полный `npm.cmd test`;
- ручной LuCI-сценарий, где одна команда доступна из двух панелей и обе панели
  обновляются без второго backend-вызова.

Модельный тест не доказывает порядок реального RPC-ответа и перерисовки DOM на
установленном роутере.

## Когда пересматривать

- LuCI-команды становятся идемпотентными и получают server-side operation ID;
- callbacks переносятся в единый реактивный store, который сам обновляет все панели;
- разные действия вынужденно получают одинаковый ключ, хотя их backend-смысл
  различается.
