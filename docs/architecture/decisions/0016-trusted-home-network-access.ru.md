# ADR-0016: Доступ к Sheepfold из доверенных сегментов домашней сети

- Статус: Принято как архитектурное направление, реализация поэтапная
- Дата: 2026-07-30
- Теги: `§homen01`, `§pairux1`
- Связанные документы: [план домашнего доступа](../../home-network-access.ru.md), [Android/OpenWrt API](../../android-openwrt-api.ru.md), [безопасность](../../security.ru.md)

## Контекст

Sheepfold может быть установлен не на том роутере или точке доступа, к которой подключён телефон. Простой доступ только к default gateway не находит такой сервер. Безусловное открытие API на WAN создаёт лишнюю поверхность атаки, а port forwarding не позволяет надёжно отличить несколько телефонов за NAT.

QR уже является короткоживущим и одноразовым. Дополнительная сверка второго кода уменьшила бы риск кражи первого использования, но усложнила бы основной путь родителя.

## Рассмотренные варианты

1. Открыть `5201` на любом WAN/RFC1918-интерфейсе. Отклонено: частный адрес не доказывает принадлежность домашней сети, а общий `/www` может открыть чужие CGI.
2. Автоматически настраивать UPnP/NAT-PMP/PCP и проброс порта. Отклонено: интернет-доступ не является целью, жизненный цикл правил ненадёжен.
3. Установить простой port-forward helper на дочерний роутер. Отклонено как основной путь: исходящий маршрут обычно уже существует, а NAT всё равно скрывает личность телефона.
4. Добавить второй код подтверждения одновременно в Android и LuCI. Отклонено ради понятного одношагового сценария; остающийся риск компенсируется предупреждением, TTL, одноразовостью, rate limit и SPKI.
5. Явно регистрировать доверенные локальные сегменты, публиковать минимальный список endpoint и сохранять end-to-end HTTPS. Выбрано.
6. Для будущих NAT-сегментов использовать криптографическую Android-идентичность или ограниченный satellite-agent. Выбрано как отдельный поздний этап после измерений.

## Решение

Sheepfold может принимать Android API на дополнительных адресах только явно доверенной домашней сети. API сначала изолируется в отдельном web root, firewall открывает только выбранный интерфейс и порт, а Android принимает адрес только после SPKI-проверки.

Сопряжение остаётся без второго проверочного кода. Первый телефон, успешно использовавший действующий QR, получает credential, после чего backend атомарно сжигает код. LuCI явно предупреждает не показывать и не пересылать QR.

Discovery-документ может сообщать минимальный список локальных endpoint всем клиентам доверенного сегмента, но список не содержит секретов и является только подсказкой. Доверие подтверждает TLS/SPKI.

Простой port-forward helper не создаётся. Если реальные routed/NAT-топологии потребуют промежуточного компонента, проектируется отдельный least-privilege `sheepfold-satellite`, а не универсальный пробросчик.

## Последствия

- Телефон сможет подключаться к Sheepfold на другом роутере той же домашней сети.
- Дополнительные сегменты не становятся доверенными автоматически.
- До изоляции API и firewall lifecycle функция остаётся выключенной.
- Текущий MAC-bound credential поддерживает только сценарии, где backend видит реальный MAC телефона.
- NAT-поддержка потребует отдельной криптографической идентичности и нового ADR.
- Пользователь не получает дополнительный экран сравнения кодов.
- Риск первого использования сфотографированного QR остаётся документированным.

## Проверка

До релиза обязательны:

- отрицательный тест доступа к LuCI через API-порт;
- live-router схема `192.168.2.x -> 192.168.2.179:5201`;
- SPKI mismatch;
- повтор QR;
- NAT/gateway-MAC refusal;
- смена порта и адреса;
- restart, upgrade и uninstall cleanup;
- Podkop/AdGuard Home matrix.

Эти тесты подтверждают локальные границы, но не доказывают безопасность прямого интернет-доступа. Интернет-доступ этим ADR запрещён.

## Когда пересматривать

- Появились реальные случаи кражи первого использования QR.
- Требуется поддержка нескольких NAT-сегментов.
- Android device-key успешно проверен на Android 9 и слабом OpenWrt.
- Появился стандартный OpenWrt-механизм безопасного локального service discovery и доверия между роутерами.
