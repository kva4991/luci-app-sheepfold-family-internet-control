# ADR-0013: Строгая JSON/form-граница AI backend

- Статус: Принято
- Дата: 2026-07-27
- Теги: `§jsonio1`
- Связанные документы: `docs/ai-assistant-development/current-implementation.ru.md`, `CODING_RULES.md`

## Контекст

AI endpoint принимает `application/x-www-form-urlencoded`, добавляет пользовательский текст к системному контексту и формирует разные JSON-запросы для DeepSeek, Gemini и Grok. Раньше gate и handler имели собственные копии percent-decoder и JSON escaping на `sed`/`printf`.

Такой код выглядит коротким, но работает на границе недоверенного ввода:

- повреждённый `%XX` мог декодироваться неоднозначно;
- NUL невозможно безопасно сохранить в POSIX shell-переменной;
- ручное экранирование легко пропускает управляющий символ либо расходится между двумя endpoint;
- строковая сборка вложенного provider payload смешивает данные и JSON-синтаксис;
- исправление одной локальной копии не исправляет вторую.

## Рассмотренные варианты

1. Оставить локальные `sed`/`printf` helpers и расширить набор замен. Это почти не увеличивает пакет, но сохраняет дублирование и хрупкую ручную сериализацию.
2. Добавить большой внешний JSON/parser runtime. Он даст богатый API, но увеличит зависимости роутера ради двух AI endpoint.
3. Использовать уже обязательный OpenWrt `jshn` для JSON и одну небольшую AI-only shell-библиотеку для строгого form-urlencoded.

## Решение

- Динамический JSON ошибок и запросов провайдеров строится только функциями `jshn`.
- Общая `sheepfold-lib-json` строго разбирает `%XX`, преобразует `+` в пробел и отклоняет malformed escape либо NUL.
- Gate и handler используют один helper и не имеют собственных `json_escape`, `url_decode` или `form_get`.
- Статические JSON-константы без пользовательских значений можно оставить строковыми литералами.
- Helper входит только в AI Support-вариант: Standard-пакету эта поверхность и зависимость выполнения не нужны.
- Отсутствие helper или `jshn` приводит к структурированной локальной ошибке до обращения к внешнему провайдеру.

## Последствия

- Пользовательский текст больше не соединяется вручную с JSON-синтаксисом.
- Правило декодирования одинаково на обеих стадиях запроса.
- Повреждённый запрос отклоняется предсказуемо и не уходит внешнему оператору.
- Библиотека зависит от поведения BusyBox `awk` и штатного `jshn`, поэтому их наличие и фактическое provider payload нужно проверять на OpenWrt.
- Это не защищает содержимое уже разрешённого AI-запроса от внешнего провайдера; маскирование и согласие остаются отдельными границами.

## Проверка

- `node --test tests/aiJsonBoundary.test.mjs`
- полный `npm.cmd test`
- `sh -n` для helper, gate, handler и runtime hardening;
- read-only `tools/router-testing/remoteChecks.sh` на AI Support проверяет chat и
  Gemini payload с кавычками, обратным слешем, табом, переводом строки и русским
  текстом через настоящий `jshn`, не обращаясь к провайдеру;
- повреждённый `%XX` дополнительно проверяется локальным form-decoder тестом.

Локальный fake `jshn` и синтаксическая проверка не доказывают совместимость с конкретной версией libubox на роутере.

## Когда пересматривать

- AI endpoint переносится с shell CGI на типизированный ucode/ubus service.
- OpenWrt убирает либо существенно меняет `jshn`.
- Появляется общий HTTP body parser с теми же строгими гарантиями и меньшей сложностью сопровождения.
