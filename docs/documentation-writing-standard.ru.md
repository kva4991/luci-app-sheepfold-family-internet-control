# Стандарт технической документации Sheepfold

<!-- §docwrit -->

Этот документ адаптирует рекомендации по ясной технической документации к Sheepfold. Его задача — уменьшить неоднозначность, устаревшие обещания и повторное расследование уже известных деталей. Он не требует механически переписывать существующие документы ради единого литературного стиля.

## Приоритет правил

Применяйте источники в следующем порядке:

1. Явное актуальное решение владельца проекта.
2. Корневой `AGENTS.md`, профильный документ, действующий ADR и точные контракты кода или схемы.
3. Этот стандарт.
4. [Google Developer Documentation Style Guide](https://developers.google.com/style/) для вопросов, которые не решены правилами Sheepfold.

Отступайте от общего правила, если это делает русский текст понятнее или сохраняет точный термин внешнего контракта. Используйте выбранный вариант последовательно.

## Достоверность документации

Перед записью существенного утверждения проверьте код, тест, UCI-схему, API, интерфейс или свежий результат выполнения. Явно различайте следующие состояния:

- **реализовано** — код существует и его граница подтверждена подходящей проверкой;
- **реализовано, но не проверено на живом устройстве** — локальный контракт подтверждён, а OpenWRT-роутер или Android-устройство ещё не проверены;
- **эксперимент** — изолированный прототип не входит в обычную поставку;
- **план** — требование или выбранное направление без готового runtime;
- **известное ограничение** — работающая функция имеет честно указанную границу.

Не превращайте наличие поля в LuCI, reference-модели или статического теста в утверждение о работающем backend. Если подтверждения нет, обозначьте это прямо.

## Читатель и тип документа

У каждой страницы должна быть одна основная аудитория и одна главная задача. Выбирайте форму по задаче читателя:

- вводная страница объясняет назначение и ведёт к поддерживаемым деталям;
- практическая инструкция помогает выполнить одну задачу;
- справочник фиксирует точные имена, значения, значения по умолчанию, ошибки и ограничения;
- runbook описывает безопасный повторяемый запуск и восстановление состояния;
- troubleshooting начинается с наблюдаемого симптома;
- ADR хранит причину устойчивого архитектурного решения, а профильный документ — текущее поведение.

Не создавайте новую страницу, если существующий профильный документ уже владеет темой. Не дублируйте одну процедуру в нескольких местах.

## Ясный язык

- Пишите по-русски для основной русской документации и по-английски для английского файла, не смешивая языки без необходимости.
- Используйте настоящее время для текущего поведения и явно обозначайте будущее.
- В инструкции начинайте шаг с действия и обращайтесь к читателю напрямую, когда это упрощает фразу.
- Предпочитайте активный залог, конкретные существительные и глаголы.
- Расшифровывайте редкое сокращение при первом использовании.
- Используйте один термин для одной сущности, включая одинаковый регистр.
- Убирайте рекламные оценки, вводные фразы без смысла и уверенность, которой не подтверждает источник.
- Не ориентируйте читателя только словами «выше», «ниже», «слева» или «справа». Называйте раздел или элемент интерфейса.

Для Sheepfold всегда уточняйте вид списка: белый список устройств, чёрный список устройств, белый список сайтов, чёрный список сайтов или аварийно-полезные сайты. Сохраняйте точные имена UCI, API, пакетов и команд.

## Структура Markdown

- Используйте один заголовок первого уровня на страницу.
- Не пропускайте уровни заголовков.
- Давайте разделам уникальные названия, по которым понятна их задача.
- Для английских заголовков используйте sentence case. В русском заголовке применяйте обычные правила регистра русского предложения.
- Не добавляйте номер в заголовок только ради оформления. Нумерация допустима, если она является частью устойчивой схемы, плана или ADR.
- Используйте нумерованный список, когда порядок важен, и маркированный список для независимых пунктов.
- Вводите таблицу только тогда, когда читателю нужно сравнить несколько одинаковых свойств.

## Процедуры и команды

Для исполняемого теста, скрипта или сетевого сценария соблюдайте контракт `§docops1`. Укажите:

1. Рабочий каталог и подходящую оболочку.
2. Предварительные условия и необходимые разрешения.
3. Точную команду без приглашения оболочки.
4. Назначение placeholders сразу рядом с командой.
5. Ожидаемый exit code и видимый результат.
6. Изменяемое состояние и способ его восстановления.
7. Частые ошибки и заведомо неправильные способы запуска.
8. Что успешный результат не доказывает.

Предпочитайте один поддерживаемый путь. Добавляйте альтернативу только для реально отличающегося окружения или пользователя.

## Техническое оформление и доступность

- Оформляйте как код имена файлов, пути, команды, ключи, переменные окружения, поля, методы и вводимый текст.
- Добавляйте язык к fenced code block, когда он известен.
- Объясняйте назначение блока перед ним и не помещайте в пример реальные секреты или семейные идентификаторы.
- Используйте описательный текст ссылки вместо «здесь», «эта страница» или голого URL.
- Добавляйте содержательный alt-текст к смысловому изображению.
- Не передавайте состояние только цветом, положением, формой или значком.
- Объясняйте сложную схему соседним текстом.

## Проверка

Из корня репозитория выполните:

```powershell
npm.cmd run quality:docs
git diff --check
```

После изменения навигации, §-тегов, этого стандарта, skill или документационного анализатора выполните `npm.cmd run quality:docs:all`.

Документационный аудит проверяет локальные ссылки, зарегистрированные §-теги, существование упомянутых тестов и npm-команд, один `H1`, порядок уровней заголовков, закрытие fenced code blocks и alt-текст изображений. Он не проверяет истинность утверждений, ясность языка, внешние ссылки и фактическую работоспособность команды.

## Навык агента

Проектный навык [sheepfold-documentation](../.agents/skills/sheepfold-documentation/SKILL.md) загружается при создании, существенной переработке или ревью документации. Навык остаётся коротким и направляет агента к этому каноническому стандарту, чтобы `AGENTS.md` не разрастался повторением редакционных правил.
