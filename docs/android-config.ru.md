# Конфигурация Android-приложения Sheepfold

> Этот документ описывает, как Android-клиент хранит настройки, как происходит сопряжение с роутером и какие параметры передаются по API.
> Для AI-агентов: читайте этот файл вместе с `docs/backend-design.ru.md` и `docs/android-openwrt-api.ru.md`.

---

## Общая архитектура хранения настроек

Роутер остаётся источником сохранённых семейных правил, устройств и UCI-настроек.
Android держит полученные снимки и несохранённые черновики в оперативной памяти рабочего
сеанса, но не создаёт отдельную постоянную базу семейных правил. Приложение — интерфейс
поверх роутерного API; локальные настройки самого APK и защищённая привязка хранятся отдельно.

| Что хранится на Android | Что хранится на роутере |
|---|---|
| Адрес роутера (IP / hostname) | Все UCI-настройки Sheepfold |
| Порт API (по умолчанию 5201) | Токены аутентификации (хэши) |
| Логин текущего администратора | Списки устройств, групп, расписаний |
| Снимки, черновики форм и фильтры устройств в RAM рабочего сеанса | API-ключи DeepSeek / Gemini |
| Тема оформления (системная / светлая / тёмная) | Токен мессенджера |
| Язык приложения | — |
| Принятая редакция соглашения и время принятия | — |

## Первоначальная настройка (First Setup)

### Порядок экранов при первом запуске

1. **Соглашение** — чекбокс «Я принимаю пользовательское соглашение…» обязателен до продолжения.
2. **Подключение к домашней сети** — требуется Wi-Fi или Ethernet до роутера; продолжение по мобильной сети заблокировано.
3. **Проверка MAC-адреса Wi-Fi** — если для этой сети включена рандомизация MAC, показывается инструкция и требуется подтверждение после переключения на реальный MAC. Если подключение по Ethernet — предупреждение о видимом MAC, инструкция Wi-Fi пропускается.
4. **Сопряжение с роутером** — сканирование QR-кода из LuCI или ручной ввод (адрес, логин, код сопряжения).
5. **Локальный PIN / пароль приложения** — рекомендуется PIN или пароль; биометрика предлагается как дополнительный вариант с предупреждением.

На первых трёх шагах круглая кнопка «Далее» завершает прокручиваемую страницу, не закрепляется у края экрана и не перекрывает текст. В ней используется сплошная стрелка `actionNext` из [общего каталога](icon-catalog.ru.md). Активная и неактивная стрелки сохраняют контраст с собственным фоном; неактивная кнопка не разрешает обойти соглашение или проверку сети (§uicontrast).

### QR-код сопряжения

Текущий формат payload: `SF2|h=<адрес>|p=<порт>|u=<логин>|c=<код>|spki=<SHA-256>`

- `h` — IP-адрес или hostname роутера
- `p` — порт Sheepfold API
- `u` — логин администратора
- `c` — одноразовый код (10 символов, генерирует роутер)
- `spki` — SHA-256 отпечаток публичного TLS-ключа роутера

Tokен действует **10 минут** и после успешного сопряжения сразу аннулируется бэкендом.
Ответ `/pair` ещё не сохраняется как готовое подключение: APK выполняет обычный авторизованный запрос к роутеру и открывает главное окно только после подтверждения, что токен связан с устройством администратора в основном UCI-конфиге (§pairtx1).

### Поворот экрана во время настройки

Шаг мастера, отметка соглашения и причина повторной привязки сохраняются через `rememberSaveable`. Одноразовый запрос сопряжения и проверенный результат принадлежат `RouterSetupViewModel` основной Activity, а не coroutine scope экрана Compose. Поэтому поворот не отменяет уже отправленный `/pair` и не запускает его повторно. Пока запрос выполняется, повторное нажатие и переход назад блокируются.

Причина решения: на телефоне роутер уже выдал токен, но при повороте Compose отменил проверку прав с `LeftCompositionCancellationException`. Это была отмена жизненным циклом, а не доказанный сетевой тайм-аут. `CancellationException` не превращается в сообщение об отказе роутера. [Android ViewModel](https://developer.android.com/topic/libraries/architecture/viewmodel) сохраняет операцию при пересоздании Activity, но не при гибели процесса.

Промежуточные Bearer, QR-код и TLS pin не записываются в saved-state Bundle. Если процесс завершился до окончания первоначальной настройки, нужен свежий QR, а не автоматический повтор прежнего кода. После потери промежуточного результата шаг защиты возвращает выбор сопряжения, а не падает. После завершения мастер освобождает свой результат; штатное защищённое хранилище сохраняет готовую привязку. Набранные, но ещё не отправленные секреты формы при пересоздании могут очищаться.

Регрессия lifecycle и визуальная проверка: [ручной Android-стенд](../tools/android-testing/parent-router-integration/README.ru.md). Синтетический тест не заменяет настоящее QR-сопряжение.

### Потеря сохранённой привязки

Для диагностики тестовый APK записывает `router.request.started/completed/failed`: HTTP method,
путь без query, длительность и тип ошибки. Заголовки, тело запроса/ответа, токен и текст исключения
в эти события не попадают. При timeout обновления главного экрана показывается локализованное
«Роутер не ответил вовремя. Повторите обновление данных.», привязка сохраняется.

Тайм-аут после успешной привязки может возникнуть до формирования ответа: общая проверка
администратора тоже выполняется на каждом запросе. Убраны повторные allocator/commit при чтении
корректных номеров устройств. Диагностика двух задержек и границы repair описаны в
[паспорте устройства](device-passport-and-control.ru.md#стоимость-чтения-списка-устройств).
Физическое сопряжение через QR-файл и paired GET проверены 30.08.2026; это не тест камеры QR.

Окончательный отказ авторизации и временная недоступность роутера обрабатываются по-разному (§authrs1):

- HTTP `401` и явные коды `invalid_token`, `token_invalid`, `token_expired` или `token_revoked` удаляют сохранённую роутерную сессию и сразу открывают выбор QR-кода/ручного подключения;
- `device_unbound` означает, что админское устройство отвязано на роутере; APK показывает: «Доступ отозван на роутере. Выполните привязку заново»;
- несовпадение закреплённого HTTPS/SPKI-отпечатка останавливает соединение. После законной замены сертификата новый отпечаток принимается только свежим локальным QR из LuCI; ручного экрана принятия длинного отпечатка нет;
- тайм-аут, отсутствие сети, `5xx` и временная недоступность роутера не удаляют токен;
- соглашение, разрешения Android и уже выбранная защита приложения не настраиваются повторно. При холодном запуске сохранённая защита по-прежнему должна разблокировать приложение;
- старый одноразовый код не сохраняется и не используется повторно. Если QR hostname разрешился в несколько локальных IP, APK сначала выбирает доступный endpoint безопасным `GET /ping` и лишь затем один раз отправляет код в `/pair`. После неоднозначного тайм-аута нужна новая попытка с новым QR-кодом или временным кодом из LuCI. Экран камеры не отправляет постоянно видимый payload по кругу, после неудачи сразу принимает новый QR, а намеренный повтор того же кода возможен после того, как пользователь убрал его из кадра и навёл снова (§dscqr01).
- LuCI не считает код использованным только потому, что телефон распознал изображение. После подтверждённого backend-статуса `paired=1`, который означает завершённую привязку и сжигание кода, QR бледнеет и поверх него появляется текст «QR-код использован». Статус остаётся видимым перед автоматическим закрытием модалки (§dscqr01).

При запуске родительского APK сохранённое подключение читается один раз. Его Bearer, ID/MAC и TLS/SPKI-отпечатки привязаны к идентичности этого экземпляра и не должны теряться после сборки мусора. Поэтому `RouterConnectionRequest` нельзя превращать в `data class`, а навигации и фоновой работе нельзя отдельно перечитывать одну сессию только ради `hasConnection()` (§authrs1).

Редакция соглашения и время её принятия хранятся отдельно от роутерной сессии. Существенное изменение соглашения требует нового чекбокса, но не повторяет Android-разрешения, QR-сопряжение и настройку защиты приложения.

## Обновление данных открытой панели

<!-- §andpanel1 -->

Кнопка «Обновить» и вход на вкладку используют один `RouterPanelLoader`. При каждом повторном
входе данные запрашиваются заново; скрытые панели не опрашиваются. Результат предыдущего
посещения может оставаться видимым во время загрузки, но не считается новым успешным чтением.

| Панель | Запросы при входе и обновлении |
|---|---|
| Управление, Информация | Только `GET /router-info` |
| Устройства, списки устройств, расписания, группы, администраторы | `GET /devices`, затем `GET /api/v1/admin-config` |
| Wi-Fi | `GET /api/v1/admin-config`, при `wifiChannelsRead=true` отдельный `GET /api/v1/admin-config/wifi/channels`, затем `GET /router-info` |
| Уведомления | `GET /api/v1/admin-config`, `GET /access-requests`, `GET /notifications` |
| Журнал | `GET /api/v1/admin-config`, затем `GET /log?lines=300`, только если разрешён `logRead` |
| Меню, локальные настройки APK | Без запросов к роутеру |
| Отзыв, ИИ | Без фонового обновления при входе; собственные запросы по явному действию пользователя |

Здесь указаны пути относительно `/cgi-bin/sheepfold-api`. Существующие ответы `router-info` и
`admin-config` общие и могут содержать поля нескольких экранов. Новый серверный API ради фильтрации
этих полей не вводится: загрузчик выбирает минимальный набор запросов для панели.
Исключение по назначению: новый optional endpoint каналов Wi-Fi вызывается только на Wi-Fi,
а не внутри общего `admin-config`. Авторизация и TLS pin остаются прежними.

`OperationalMainScreen` применяет набор ответов панели целиком. Если второй запрос завершился
ошибкой, частично загруженные данные не заменяют прежнюю пару «устройства + правила». Ошибка
видна на открытой панели. При переходе на другую вкладку Compose отменяет ожидание старого
чтения; поздний ответ не применяется и не снимает индикатор новой панели. Уже отправленный
HTTP GET при этом может закончиться на роутере: отмена ожидания не обещает остановку CGI.

После команды включения/выключения интернета выполняется read-back только `control`, то есть
`/router-info`. Кнопки остаются заблокированными до подтверждения фактического состояния.
Переход между вкладками не повторяет отправленную команду. Текущая вкладка сохраняется при
повороте, но после пересоздания экрана её данные читаются заново.

Фоновый `AccessRequestWorker` остаётся независимым: его 15-минутный WorkManager-план не зависит
от кнопки «Обновить». Вкладка «Уведомления» дополнительно доставляет найденные события через
прежние helpers с защитой от повторных уведомлений. Обновление управления не запрашивает их.

Причина: общий refresh раньше выполнял пять последовательных GET, хотя главному экрану нужны
только название и текущее состояние доступа. Разделение снижает нагрузку на маломощный роутер
и не связывает открытие управления с отказом журнала или уведомлений. Проверки и ограничения:
[профиль Android-стенда](../tools/android-testing/parent-router-integration/README.ru.md#обновление-открытой-панели).

### Где находится ручное обновление

На Wi-Fi значок обновления находится рядом с главным переключателем. Он нужен в том числе
после разрыва связи при сохранении сети; повторное чтение не отправляет настройки заново.

В родительском APK кнопка «Обновить» со значком `actionRefresh` расположена в начале
вкладки «Информация», под заголовком и перед диагностическими полями. Она видна и без
первого успешного ответа; во время загрузки отключена. Нажатие использует тот же
`RouterPanelLoader` и только `GET /router-info`, без сохранения настроек.

В детском APK кнопка «Обновить данные» в две строки расположена вверху вкладки «Статус»,
над карточкой результата или ошибки. Общая кнопка заменяет прежние копии внутри карточек,
чтобы оставаться доступной при длинном тексте; содержимое под ней прокручивается.
Во время запроса или без адреса роутера кнопка отключена. Она вызывает прежний
`ChildStatusViewModel.refresh()` и чтение статуса устройства, не продлевает доступ и
не меняет правила. Ошибка соединения не считается подтверждением отключённого интернета.

Порядок элементов и привязку callbacks проверяют `tests/androidParentManagement.test.mjs`
и `tests/childAccessStatusTime.test.mjs`. Это проверки исходников, не имитация нажатий;
проверка на телефоне описана в [Android-стенде](android-test-lab.ru.md).

### Неизвестное состояние интернета

`ParentWorkspace` отдельно хранит последний `RouterSnapshot`, время его получения на телефоне
и признак `controlUnknown`. До первого ответа обе плашки управления отключены, внутри указано
«Получаем состояние». После ошибки чтения или неоднозначного результата команды обе плашки
тоже отключены: старое значение `globalBlocked` не выдаётся за актуальное. Показываются
«Состояние интернета неизвестно» и дата/время последних успешно полученных данных, если они есть.
Кнопка обновления остаётся доступной после завершения запроса. Успешный `/router-info`
восстанавливает известное состояние; POST без подтверждающего чтения этого не делает.

`diagnostics.globalBlocked` должен быть ровно `0` или `1` (в строковом представлении JSON).
Отсутствие, пустая строка и другое значение вызывают ошибку, а не разрешённый интернет.
Это состояние глобального выключателя Sheepfold, не обещание доступности всех сайтов/WAN.
Потеря связи определяется не непрерывным опросом, а неудачным запросом; отметка времени
показывает давность последнего подтверждения. Фоновых частых запросов не добавлено.

### Черновики рабочего сеанса

`ParentWorkspace` принадлежит `MainActivity` через `ViewModel`. Формы устройства, группы,
расписания, Wi-Fi, Wi-Fi-автоматики, настроек уведомлений и текста отзыва живут в RAM.
Они сохраняются при повороте экрана, переходе между вкладками и локальной блокировке APK.
Настройки записываются на роутер только по явной кнопке сохранения. Закрытие изменённого
модального редактора требует подтверждения отмены; Wi-Fi и уведомления имеют явную отмену.

`FormDraft` хранит исходную запись и её `revision`/`wifiRevision`, независимо от позднего GET.
Новый снимок не затирает изменённую форму и не даёт права молча перезаписать чужие изменения.
При `revision_conflict` форма остаётся открытой с ошибкой. Автоматического объединения правок
пока нет: нужно сверить актуальные данные, явно отменить старый черновик и повторить изменение.
Неизменённые формы Wi-Fi/уведомлений принимают новую ревизию. Если новый GET Wi-Fi совпадает
с отправленным черновиком, он становится подтверждённым исходным состоянием.

Запись основных редакторов использует scope ViewModel: поворот не запускает её повторно.
Поля блокируются на время отправки. Отзыв сохраняет введённый текст, но незавершённое окно
предпросмотра/отправка отчёта не обещают восстановления после поворота: явное согласие и HPKE
остаются отдельной границей. Выбор нескольких устройств в модалке списков ещё не перенесён
в этот механизм. Не заявлять сохранность всех возможных модальных операций приложения.

При смене роутера/токена, отзыве доступа или явном отключении `workspace.clear()` очищает RAM
и отменяет собственные задачи. После уничтожения процесса Android черновики не восстанавливаются.
Wi-Fi-пароли, текст отзывов и снимок admin-config не записываются в `SavedStateHandle`, Bundle
или обычные файлы ради восстановления формы. Это сознательная граница текущего решения.

### Действия, уведомления и предпросмотр расписания

В карточках устройства постоянные действия находятся в «Правила доступа» и названы «В белый список устройств»
и «В чёрный список устройств»; временная команда называется «Разрешить интернет на 30 минут».
Она не выводит устройство из чёрного списка устройств и не отменяет более приоритетные правила.
Точное время окончания APK не придумывает по своим часам: текущий ответ команды его не содержит.
Во вкладке уведомлений сначала идут события, затем настройки их получения.

Редактор расписания показывает семь дневных полос с часами. Он использует `scheduleWindows`
из общего расчёта конфликтов; `previewDayWindows` разрезает ночные интервалы, включая переход
воскресенья в понедельник. Выключенное правило показывает пустые полосы и подпись.
Это предпросмотр конкретного правила в часовом поясе роутера, не симуляция итогового доступа.
Предупреждение о конфликте с противоположным правилом сохранено; ограничения сравнения целей
не расширены до полного firewall-вычислителя. Для TalkBack у каждой полосы есть день и интервалы.

Владелец согласовал макет 31.08.2026. Общий `DeviceCard` используется в устройствах и списках
устройств: имя, группа и назначенное **правило** остаются на первом плане, ID/IP/MAC/тип открываются
через «Подробнее». В «Правила доступа» доступны постоянные команды и переход к редактированию
устройства; администратор не получает обычные семейные команды. Во временной команде явно указаны
30 минут. `/devices` пока отдаёт UCI-политику, не online и не фактический итог firewall: карточка
не подменяет её надписью «Интернет разрешён», как было на иллюстративном макете. Ни присутствие,
ни время последнего подключения из сохранённого IP не выводятся. `DeviceCardsPreviewTest` теперь
снимает настоящую карточку с синтетическими данными. Упрощение диагностики ждёт согласования.

### Фильтры устройств

В «Устройствах» и в каждой под-вкладке списков устройств доступен выпадающий фильтр «Показать»:
«Все», «Персональные устройства» (умолчание), «Мультимедиа», «Технические», «Умный дом»,
«Носимые устройства», «Неизвестные».
`DeviceFilter` применяется только к загруженным данным, без API-запроса, смены группы или правил.
Белый/чёрный списки устройств сначала ограничивают выбор членством в соответствующем списке,
затем категорией. Пустой результат фильтра не означает, что устройств на роутере вообще нет.

Категории определяются по `deviceType`, не по названию или признаку personal у семейной группы:

| Категория | Типы |
|---|---|
| Персональные | Телефоны (`phone`), планшеты (`tablet`), ноутбуки и ПК (общий тип `computer`), а также носимые устройства (`smart_watch`) |
| Мультимедиа | Телевизоры, медиаплееры/ТВ-приставки, игровые приставки, колонки: `tv`, `media_player`, `console`, `speaker` |
| Технические | Принтеры, серверы/сетевые хранилища, инженерное и сетевое оборудование: `printer`, `server`, `engineering`, `network`, `router`, `network_switch` |
| Умный дом | Бытовые устройства/датчики, роботы-пылесосы, IP-камеры: `smart_home`, `vacuum`, `camera` |
| Носимые устройства | Умные часы и браслеты, распознанные общим типом `smart_watch` |
| Неизвестные | `unknown`, общий legacy `smart`, пустой или неподдержанный будущий тип |

Общий тип «Умное устройство» не доказывает принадлежность к умному дому, поэтому попадает
в «Неизвестные». Перенос телефона в группу гостей не меняет его категорию. Группировка для UI
не изменяет правила автоназначения detector. Выбор хранится в RAM рабочего сеанса и переживает
поворот/смену вкладки; у «Устройства» свой выбор, у трёх списков общий. При новом сеансе снова
выбраны персональные устройства. Новые типы необходимо явно сверять с `DeviceFilterRulesTest`.

Состав согласован владельцем 31.08.2026: мультимедиа не смешивается с техническим оборудованием,
а носимая техника входит в персональные устройства и одновременно доступна отдельным узким
фильтром. Категории здесь не полностью взаимоисключающие: `deviceCategory` для `smart_watch`
соответствует `WEARABLE`, а `filterDevices` включает его и при выборе `PERSONAL`.
Фильтр группирует уже известные типы, не добавляет детектору новых
способностей распознавания. Например, нераспознанный фитнес-браслет остаётся в «Неизвестных».

## Подписи карточек меню

В родительском APK значок карточки «Меню» расположен над названием. Текст использует
всю внутреннюю ширину, а не узкий остаток справа от значка. Минимальная ширина ячейки
определяется измерением самого длинного слова в текущих названиях с выбранным системным
масштабом шрифта, плюс отступы и запас округления. Сетка сокращает число колонок, если
слово не помещается. Высота карточки не фиксирована: она растёт от минимума 112 dp.

Размер шрифта не уменьшается ради сетки, подписи не сокращаются многоточием. Обычный
перенос фразы между словами разрешён, автоматическая расстановка дефисов отключена.
Причина: прежние ячейки от 148 dp с горизонтальным значком оставляли около 74 dp для
названия; фиксированные 86 dp по высоте дополнительно обрезали длинные подписи.
Измерение выполняется локально и кешируется, запросов к роутеру не добавляет.

`MenuLayoutTest` проверяет фактические границы строк, отсутствие обрезания и переходы
в русской/английской локализации, обеих темах и с увеличенным шрифтом. Команды и пределы
проверки находятся в [Android-стенде](android-test-lab.ru.md#меню-переносы-подписей).

## QR-коды сетей Wi-Fi

### Безопасное редактирование

Перед сохранением сети APK предупреждает о возможном разрыве связи и способе переподключения,
отдельно отмечает отключение сети, слабую защиту и другие SSID того же радиомодуля при смене канала.
Отмена подтверждения сохраняет черновик. При транспортной ошибке после отправки APK не утверждает,
что запись не состоялась: предлагает переподключиться и обновить данные, без автоматического POST.

Каналы берутся из optional authenticated `wifi/channels` через OpenWrt iwinfo, с проверкой
диапазона и `restricted`. Не используются общие списки 1–165 для любого радио. Старый backend
без capability или отсутствие iwinfo оставляют только прежний канал и `auto`, с пояснением.
Новый числовой канал дополнительно проверяется backend перед записью. [Точный контракт и лимиты](android-openwrt-api.ru.md#каналы-радиомодулей).
Проверка полей APK считает длину UTF-8, не число видимых букв; она не заменяет проверку hostapd.

### Источник QR

В родительском APK QR-код подключения расположен в самом верху каждой карточки сети,
перед её заголовком, переключателем и полями редактирования. Он строится локально из
подтверждённых роутером SSID, пароля и типа защиты. Несохранённый черновик не меняет код;
после успешного сохранения код обновляется вместе с ответом роутера. Используется прежний
квадратный чёрно-белый QR размером 220 dp, без дополнительного сетевого запроса.

Растровый encoder получает явный `CHARACTER_SET=UTF-8`: без него ZXing заменял кириллицу
и китайские символы SSID/пароля на `?`. Экранирование разделителей Wi-Fi payload остаётся
отдельной операцией. `ParentWifiTest` декодирует изображение из Compose, а `WifiQrTest`
проверяет формат и спецсимволы. Один правильный исходный текст не доказывает правильный QR.

Порядок элементов и источник данных защищены `tests/androidParentManagement.test.mjs`.
Это source-проверка: видимость нескольких карточек, сканирование другим телефоном и
портретный/альбомный режимы проверяются отдельно на [Android-стенде](android-test-lab.ru.md).

## Обнаружение роутера в сети

<!-- §dscqr01 -->

Приложение сначала проверяет discovery-файл через штатный HTTPS-порт роутера:

```
GET https://<router-ip>/.well-known/sheepfold.json
```

Если штатный HTTPS недоступен, дополнительно проверяется `https://<router-ip>:5201/.well-known/sheepfold.json`. Из ответа приложение узнаёт фактический `appPort`/`httpsPort`, после чего обязательно проверяет `GET /cgi-bin/sheepfold-api/ping`. У discovery свой счётчик запросов: исчерпанный лимит обычных API-команд не должен выглядеть как отсутствие сервера. Статический JSON без работающего API не считается найденным сервером.

Ожидаемый ответ:

```json
{
  "service": "sheepfold",
  "name": "Sheepfold Family Internet Control",
  "routerName": "OpenWRT Sheepfold",
  "appPort": "5201",
  "apiPath": "/cgi-bin/sheepfold-api",
  "apiBase": "/cgi-bin/sheepfold-api",
  "version": "0.1.0"
}
```

HTTP fallback не используется: автопоиск и сопряжение остаются только на HTTPS.

## Local-first family message relay

<!-- §mrelay1 -->

Статус: Android client foundation в source реализована и проверена unit-level; она сохраняет строгий
local-first fallback и fail-closed state transitions, но остаётся выключенной для production. relay
не подключён к production provisioning, UI или app lifecycle. Физический Android API 30 проверил
изолированные криптографические fixtures; API 28 и сквозной relay остаются непроверенными.
Native helper собран официальным SDK и проверен синтетическими векторами на тестовом роутере,
но OpenWrt poller/dispatcher/provisioning отсутствуют. Поэтому `clientsReady=no`, `realDataAllowed=no`; relay предназначен только для
родительского APK после локального сопряжения и не заменяет локальный Sheepfold API.

- `routePolicy = local_preferred`: на Wi-Fi/Ethernet сначала проверяется сохранённый локальный IP и закреплённый SPKI, затем при недоступности локального маршрута выбирается relay; на сотовой сети локальная проба пропускается;
- сбой relay не удаляет локальный Bearer и не мешает работе дома по Wi-Fi;
- relay имеет отдельную Android Keystore identity и не использует alias локального `sheepfold-admin-token`;
- `401/403` от relay отключает только relay-сессию; `device_unbound`/`revoked` от роутера завершает обе привязки;
- fallback к public relay разрешён только при доказанном отказе local route до передачи HTTP body;
- неоднозначный timeout/сбой после возможной передачи body не создаёт новый `messageId`: приложение
  сохраняет `INDETERMINATE` и выполняет lookup прежней команды. Отсутствие разрешает fallback только
  при точном аутентифицированном protocol-ответе роутера, а не по пустому/generic HTTP `404`.

**Почему выбран этот способ / нюансы.** Durable отметка local attempt до сетевого I/O и строгая
граница «body точно не отправлен» не дают fallback выполнить одну команду вторично после crash или
потерянного ответа. Exact application-level `notFound` нужен потому, что generic `404` может вернуть
старый endpoint или proxy; до реализации linearized OpenWrt lookup это остаётся integration gate.

Android уже проверяет request-bound `notFound` и сохраняет durable marker до public enqueue.
Соответствующий реальный router endpoint ещё не реализован; оставшиеся пробелы и порядок продолжения перечислены в
[`family-message-relay-continuation-plan.ru.md`](family-message-relay-continuation-plan.ru.md).

Точные сохраняемые поля, тайм-ауты, TTL, размеры очередей и server endpoints: [`android-router-message-relay.ru.md`](android-router-message-relay.ru.md).

## Тема оформления

- Значение по умолчанию: **«следовать системе»** (`system`).
- Поддерживаемые варианты: `system`, `light`, `dark`.
- Хранится локально в `SharedPreferences` / DataStore.
- Тема не отправляется на роутер и не влияет на LuCI.

## Детский APK (Child APK)

Отдельная сборка без авторизации и управляющих функций:

- Не требует входа / пароля при открытии.
- Показывает только статус текущего устройства: разрешён / ограничен / расписание.
- Кнопка «Попросить +30 минут» — отправляет запрос родителю через API роутера, не применяет самостоятельно.
- Не имеет доступа к спискам устройств, настройкам, журналу.
- Не хранит никаких токенов администратора.
- При первом запуске приложение до 30 секунд само ищет Sheepfold на шлюзе активной Wi-Fi/Ethernet-сети и проверяет `/ping` по HTTPS.
- Только если поиск не удался, показываются подсказка о возможной неверной Wi-Fi-сети, повторный поиск и ручной ввод IP-адреса. Ручной ввод не является обычным первым экраном.
- MAC и идентификатор не вводятся в APK: роутер определяет устройство по фактическому локальному соединению.

Endpoint для детского APK:
```
GET /cgi-bin/sheepfold-api/client-status
```

Ответ:
```json
{
  "status": "allowed",         // allowed | restricted | scheduled
  "schedule_name": "Учебные дни",
  "next_change_at": "20:30",
  "warning_before_minutes": 5
}
```

> Уведомление отображается за **5 минут** до ограничения (поле `warning_before_minutes`).

## AI-ассистент в Android

### Провайдеры

| Провайдер | Хранение ключа | Кто делает запрос |
|---|---|---|
| DeepSeek | На роутере | Роутер |
| Gemini Free | На роутере | Роутер |

Android **не хранит** API-ключи. Все запросы к AI проходят через роутерный прокси.

### Отправка диагностического контекста

1. Android запрашивает снимок: `GET /cgi-bin/sheepfold-api/router-info`
2. Показывает родителю предпросмотр перед отправкой.
3. Родитель подтверждает отправку.
4. Приложение отправляет данные выбранному провайдеру через роутер.

В снимке **отсутствуют**: пароли Wi-Fi, токены ботов, имена детей, MAC-адреса, списки устройств.
